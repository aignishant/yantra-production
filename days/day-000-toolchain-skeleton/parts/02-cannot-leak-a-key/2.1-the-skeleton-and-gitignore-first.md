## One-line answer

Write `.gitignore` before the first secret exists, because the rule that protects you is the one
that was already in place when you were not thinking about it.

## The story

The workshop has a locked cabinet for the things that must not walk: the master keys, the client
files, the one calibrated gauge.

The cabinet was not bought after something went missing. It was there on the first day, empty,
with a lock on it. That is the only reason it works. A cabinet bought *after* the first theft
protects everything except the thing that was already taken — and the thing that was already taken
is the one that mattered.

An empty locked cabinet looks like paranoia on day one. It is the cheapest thing in the workshop.

## The idea in plain language

A **repository** is a directory that git is tracking. Git does not track everything in it
automatically — a file becomes tracked when you `git add` it, and from then on git records every
version of it, forever, in the repository's history.

*Forever* is the word that matters. Git history is not a current state; it is an append-only log.
Deleting a file in a later commit does not remove it from the history. Anyone who clones the
repository gets every version of every file it has ever tracked.

A **`.gitignore`** file lists patterns git should refuse to add. It is how you tell git that
`.venv/` is a build artifact, that `*.safetensors` is a 5GB model checkpoint, and that `.env` holds
credentials.

The critical property, and the one part [2.2](2.2-the-secret-that-was-already-committed.md) exists
to make you feel: **`.gitignore` only prevents. It cannot undo.** A file that is already tracked
stays tracked, and adding it to `.gitignore` afterwards changes nothing at all — silently.

So the ordering is not a style preference. `.gitignore` written first prevents everything.
`.gitignore` written second prevents everything except the thing that already happened.

## Why Yantra needs it

Day 191 gives an agent an IAM role, an OAuth token and a secrets manager. Day 205 gives that agent
write access to a real GitHub repository. Day 227 makes this repository public.

Those three facts together are why the ordering matters here and not just in principle. The
discipline has to be in place long before the first credential exists, because by the time you have
an agent with a write token you are no longer thinking about `.gitignore` — you are thinking about
the agent.

## The mechanism

The skeleton, in the order the files are created. The order is the lesson.

```bash
mkdir yantra && cd yantra
git init                                   # 1. a repository, empty
printf '.env\n.venv/\n__pycache__/\n' > .gitignore   # 2. the cabinet, empty and locked
git add .gitignore && git commit -m "gitignore before the first secret exists"
cp .env.example .env                       # 3. only now does a secret exist
```

**Line by line:**

- `git init` — makes the directory a repository. Nothing is tracked yet, which is the safest state
  this repository will ever be in.
- `printf '.env\n...' > .gitignore` — written **second**, before any secret exists. `.env` is the
  credential file; `.venv/` is the environment from [1.2](../01-one-owner/1.2-uv-and-the-venv-you-never-activate.md),
  a build artifact that is rebuilt from `uv.lock` and never committed. The trailing `/` on `.venv/`
  and `__pycache__/` means "directory only" — without it the pattern would also match a *file*
  named `.venv`, which is not what you mean.
- `git add .gitignore && git commit` — committed on its own, before anything else. Committing it
  alongside the first real code is the version of this that goes wrong, because it means there was
  a window where the repository had files and no ignore rules.
- `cp .env.example .env` — **third**. `.env.example` is committed and holds the *names* of every
  variable with empty values, so a new clone can see what is needed. `.env` is the copy with real
  values in it, and it is already ignored by the time it exists.

## When it breaks

Get the order wrong and git says nothing whatsoever. That silence is the failure:

```text
$ git ls-files
.env
.gitignore

$ git check-ignore -v .env
$ echo "exit=$?"
exit=1

$ git status --short
$
```

*Observed 2026-09-07, in a repository where `.env` was committed and `.gitignore` was added
afterwards.*

**What it means:** `.env` is in `git ls-files`, so it is tracked. `git check-ignore` exits 1 and
prints nothing — its way of saying "this path is not being ignored", because ignore rules do not
apply to files git already tracks. `git status` is clean. Every tool agrees that everything is
fine, and the key is in the history.

**The smallest fix** is not small, and part [2.2](2.2-the-secret-that-was-already-committed.md) is
about why.

## In production

- **What a professional writes instead of the teaching version.** `.gitignore` is not hand-written
  per project. It is copied from a known-good baseline and then *added to*, because the failure
  mode of hand-writing it is omission, and you cannot review a file for the pattern that is not
  there. The one thing worth checking by hand every time is that `.env` is present and
  `.env.example` is explicitly un-ignored — a bare `.env*` pattern will swallow your example file
  and the next person to clone gets no idea what variables exist.
- **What degrades at scale.** This repository will eventually hold model checkpoints, GGUF
  quantizations, Qdrant snapshots and evaluation artifacts, none of which belong in git. A
  `.gitignore` that was never extended is how a repository ends up 40GB and unclonable, and the fix
  for that is the same expensive history rewrite as the fix for a leaked key.
- **The failure that only shows with real traffic.** Secret-scanning services watch public
  repositories and match key formats. A cloud key pushed publicly is often used by someone else
  within minutes — reliably faster than you will notice. Making the repository public on day 227
  is the moment every past commit becomes readable, not just the current one.
- **The review comment.** *"`.env.example` is being ignored by the `.env*` pattern — new clones
  won't know what to set."*
- **The interview question.** *"You notice a credential in a commit from three months ago. Walk me
  through what you do."* Anyone who answers "delete it and commit" has not done it. The first step
  is to rotate the key, and part 2.2 explains why.

## Check yourself

- **Run:** `git check-ignore -v .env` in the project root — expect a line naming `.gitignore` and
  the line number of the rule. If it prints nothing and exits 1, `.env` is **tracked**, and you
  need part 2.2 now rather than later.
- **Say out loud:** Why does adding a file to `.gitignore` after it has been committed change
  nothing — and what does `git status` show you while that is true?
