## One-line answer

Once a secret is in git history the only honest first step is to rotate the key, because removing
it from the history does not remove it from every clone, fork and cache that already has it.

## The story

This is the day's deliberate failure. Cause it on purpose, in a throwaway directory, and watch
every tool tell you nothing is wrong.

Back at the cabinet. The master key went missing on Tuesday. On Wednesday you buy the cabinet, fit
the lock, and put the *spare* master key inside it. The cabinet is now correct. The workshop is now
protected. And the key that went missing on Tuesday still opens every door in the building.

Buying the cabinet was the right thing to do. It was not the *first* thing to do. The first thing
was to change the locks.

## The idea in plain language

Git history is append-only by design. That is not a limitation; it is the feature the whole tool
is built on — a commit hash is a fingerprint of its content and everything before it, which is what
makes history verifiable.

The consequence is that "remove this file from the repository" and "remove this file from the
repository's history" are completely different operations. The first is `git rm`, it is one
command, and it leaves every past version in place. The second rewrites every commit from the leak
onward, which changes every subsequent hash, which means every clone of that repository now has a
history that no longer matches.

And even a successful rewrite does not help, because by then the secret has usually been copied
somewhere you do not control:

- every clone anyone made, including CI runners that cached the repository;
- every fork, which is a separate repository the rewrite cannot touch;
- the hosting provider's own caches, which can serve an "unreachable" commit by hash for some time
  after the rewrite;
- any backup, mirror or code-search index that fetched it.

This is why the ordering of the response is fixed: **rotate first, clean second.** Rotating makes
every leaked copy worthless in one step, and it is a step you fully control. Cleaning is
housekeeping done afterwards on a key that no longer works.

## Why Yantra needs it

This repository accumulates credentials the whole way through: provider keys from phase 5, a Hugging
Face token from phase 2, a Neo4j password from phase 15, and from phase 19 an agent identity with
delegated access to real systems. Then day 227 makes the repository public.

If the discipline is not automatic by then, the audit on day 227 is where you find out — and that
audit reads every commit, not the current tree.

## The mechanism

Cause it. Use a throwaway directory and a key that is obviously fake.

```text
$ mkdir /tmp/leak && cd /tmp/leak && git init -q .
$ printf 'OPENAI_API_KEY=sk-not-a-real-key-0000\n' > .env
$ git add .env && git commit -qm "oops"        # the mistake
$ printf '.env\n' > .gitignore                  # the reflex that does not work
$ git add .gitignore && git commit -qm "add gitignore"
$ git ls-files                                 # is .env still tracked?
.env
.gitignore
```

*Observed 2026-09-07.*

**Line by line:**

- `git add .env && git commit -qm "oops"` — the mistake, and it takes one distracted moment. `git
  add .` would have done it just as well without you naming the file at all, which is how it
  usually happens.
- `printf '.env\n' > .gitignore` — the reflex. It is the correct file with the correct content, and
  against a *tracked* file it does nothing, because ignore rules are consulted when deciding
  whether to start tracking something, not on every operation afterwards.
- `git ls-files` — the only command in this sequence that tells you the truth. `.env` is still
  listed. Prefer this over `git status`, which is silent here: `status` reports *changes*, and
  nothing changed.

Now the partial fix:

```text
$ git rm --cached .env
rm '.env'
$ git ls-files
.gitignore
```

**Line by line:**

- `git rm --cached .env` — untracks the file **without deleting it from disk**. Omit `--cached` and
  you delete your own credentials, which is a bad afternoon on top of a bad afternoon.
- The second `git ls-files` — `.env` is gone from the index. From here on it is correctly ignored.
- **What has not happened:** the commit named `oops` still contains the key. `git log -p` will show
  it. This fix protects the future and does nothing about the past, which is the entire point of
  this part.

## When it breaks

The most misleading moment is `git check-ignore` on a tracked file:

```text
$ git check-ignore -v .env
$ echo "exit=$?"
exit=1

$ git status --short
$
```

*Observed 2026-09-07.*

**What it means:** exit code 1 from `check-ignore` means "this path is not ignored". It prints
nothing at all — no rule, no explanation. Read quickly, an empty output plus a clean `git status`
reads as *everything is fine*. It means the opposite: the file is not ignored, because it is
tracked.

**The smallest fix** for the tracking is `git rm --cached .env`. **The smallest fix for the leak is
to rotate the key**, and those are not the same sentence.

## In production

- **What a professional does instead of the teaching version.** They do not rely on remembering.
  Pre-commit hooks that scan staged diffs for key-shaped strings, and provider-side secret scanning
  on the hosting platform, both run without anyone deciding to run them. The human rule is the last
  line, not the first.
- **The response order, which is the actual professional knowledge.** Rotate the credential.
  Check the provider's audit log for use between the leak and the rotation — this is the step
  people skip, and it is the one that answers "did anything happen?". Then untrack, then decide
  whether a history rewrite is worth the disruption. On a repository with collaborators or forks it
  frequently is not, once the key is dead.
- **What degrades at scale.** In a monorepo with four services and a CI pipeline, a rewrite
  invalidates every open branch, every cached checkout and every in-flight pull request. The
  cleanup can cost more engineering hours than the incident, which is why rotation-first is not a
  shortcut — it is the proportionate response.
- **The failure that only shows with real traffic.** Automated scrapers watch public pushes for key
  formats. The window between "pushed" and "used by a stranger" is routinely measured in minutes,
  which is faster than a human notices and much faster than a history rewrite completes.
- **The review comment.** *"This PR removes the key from the file but the commit that added it is
  still in the branch. Has it been rotated?"*
- **The interview question.** *"A key was committed to a public repo an hour ago. What is your
  first action?"* "Rewrite the history" is the wrong answer and a common one. The right first
  action is rotation, and being able to say *why* — because you control rotation and you do not
  control who already has a copy — is the whole answer.

## Check yourself

- **Run:** the mechanism above in `/tmp`, ending with `git log -p | grep sk-not-a-real-key` —
  expect **the fake key to still appear** after `git rm --cached`. That is the lesson: you removed
  the file and the history kept it.
- **Say out loud:** Why is rotating the key the first step rather than the last, when rewriting the
  history feels like the more thorough fix?
