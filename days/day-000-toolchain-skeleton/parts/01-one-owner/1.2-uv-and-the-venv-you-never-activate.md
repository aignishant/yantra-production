## One-line answer

`uv run` picks the project's interpreter for you, which means you never type `source
.venv/bin/activate` again — and never again debug a command that quietly used the wrong Python
because you forgot to.

## The story

Back at the tool board: the rule is that you sign a tool out before using it. It is a good rule.
Everyone agrees with it. And on a normal day, with one job, it works.

Then you are three jobs in, someone calls you over to look at a seized hinge, you pick up the
nearest driver without thinking, and you are working with an unsigned tool. Nobody was careless.
The rule just needed you to remember something at exactly the moment you were thinking about
something else.

The rules that survive are the ones that do not need remembering. A tool that will not turn unless
it is signed out beats a sign-out sheet, every time.

## The idea in plain language

Activating a virtual environment means running a script that edits your shell's `PATH` so that
`python` and `pip` resolve to the ones inside `.venv/` instead of the system's. It is a temporary
edit to the current shell, and it lasts until that shell closes.

Two things follow, and both bite.

**It is invisible.** Nothing about your prompt necessarily tells you whether it happened. You have
one shell where it did and one where it did not, and they look the same.

**It does not survive.** A new terminal tab is not activated. A script run by a scheduler is not
activated. A build step in CI is not activated. Every one of those places is somewhere a command
will silently run under the wrong interpreter.

The alternative is to make the interpreter part of the command rather than part of the shell.
`uv run <command>` looks at the project directory, finds the venv that belongs to it, creates it
if it is missing, syncs it against the lockfile if it is stale, and *then* runs the command inside
it. There is no state to forget, because there is no state.

`uv` is a single binary that also handles the jobs that used to need several tools: creating the
venv, installing the interpreter itself if the required version is absent, resolving dependencies,
and writing the lockfile. That consolidation is the point — one tool owning the environment, as
[1.1](1.1-why-one-tool-owns-the-environment.md) argued.

## Why Yantra needs it

Day 215 puts the evaluation suite into a GitHub Actions workflow. A workflow step is a fresh
non-interactive shell with nothing activated. If your daily habit is `source .venv/bin/activate &&
pytest`, that habit does not translate, and the first CI run fails on something unrelated to the
change that triggered it.

Everything in this repository — the checks, the depth contract, the eval gates — is written to be
runnable by a machine that will never activate anything.

## The mechanism

The whole setup, and the proof that nothing was activated:

```text
$ uv init --name yantra        # creates pyproject.toml
$ uv add ruff                  # resolves, installs, records
Resolved 2 packages in 481ms
Installed 1 package in 220ms
 + ruff==0.16.6
$ uv run python -c "import sys; print(sys.executable)"
/tmp/d0lab/.venv/bin/python3
```

*Observed 2026-09-07.*

**Line by line:**

- `uv init --name yantra` — writes `pyproject.toml`, the file that declares what this project is
  and what it needs. It does not create the venv yet; the venv is a build artifact and gets made on
  first use, which is why `.venv/` is gitignored and `pyproject.toml` is not.
- `uv add ruff` — three operations in one, per [1.1](1.1-why-one-tool-owns-the-environment.md):
  resolve, install, record. The `+ ruff==0.16.6` line is the resolution result, and the exact
  version is what lands in `uv.lock`. Prefer this over editing `pyproject.toml` by hand — hand
  edits do not update the lockfile, so the two files start to disagree.
- `uv run python -c "..."` — `uv run` is doing the work here. Note what is absent: no `source`, no
  activation, and the shell's own `python3` is untouched.
- The output path `/tmp/d0lab/.venv/bin/python3` — this is the proof. The command asked the
  interpreter to name itself, and it named the project's, not the system's, in a shell where
  nothing was activated.

## When it breaks

The failure mode is not an error. It is the absence of one:

```text
$ which python3
/usr/bin/python3
$ python3 -c "import ruff"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'ruff'
```

*Observed 2026-09-07, in the same directory where `uv add ruff` had just succeeded.*

**What it means:** the package is installed — into the project's venv. The bare `python3` is the
system interpreter, which has never heard of it. Nothing is broken; you asked the wrong Python.

**The smallest fix:** `uv run python -c "import ruff"`.

**Why this one is worth causing on purpose:** the error names the package, so the instinct is to
install the package again. Doing that with `pip` is exactly how the second spanner gets onto the
bench. The error is about *which interpreter*, and it never says so.

## In production

- **What a professional writes instead.** Every command in a README, a Makefile, a CI workflow or a
  Dockerfile is prefixed with the runner. Not because activation is wrong, but because a command
  that depends on invisible shell state cannot be copied into a file and trusted. If a command in
  your documentation only works after a step the documentation does not mention, the documentation
  is wrong.
- **What degrades at scale.** With one project, activation is fine. With four services in one
  repository — which is what this curriculum builds — the question "which venv is this shell in?"
  has four wrong answers, and the cost of guessing wrong grows with the number of services.
- **The failure that only shows with real traffic.** A cron job or a scheduled evaluation run
  inherits a minimal environment. Code that worked interactively for weeks fails at 3am with a
  `ModuleNotFoundError` for something that is definitely installed — because the schedule's shell
  never activated anything.
- **The review comment.** *"This script assumes an activated venv. Run it through `uv run` so the
  workflow can call it too."*
- **The interview question.** *"What does activating a virtual environment actually do?"* The
  answer that shows you have used one in anger is that it edits `PATH` in the current shell only —
  and the follow-up worth volunteering is why that makes it a bad foundation for automation.

## Check yourself

- **Run:** `uv run python -c "import sys; print(sys.executable)"` in the project root, in a shell
  where you have activated nothing — expect a path ending in `.venv/bin/python3`, **not**
  `/usr/bin/python3`.
- **Say out loud:** Name two places a command will run where nobody has activated a virtual
  environment, and say what happens there if your project depends on activation.
