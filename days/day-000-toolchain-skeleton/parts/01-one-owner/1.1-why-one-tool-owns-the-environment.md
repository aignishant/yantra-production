## One-line answer

Every Python problem that starts with "but it works on my machine" is the same problem — more than
one thing is allowed to decide which interpreter and which packages you get — and the fix is to
give that decision to exactly one tool.

## The story

A shared workshop has a tool board with the outline of every tool painted behind it. Spanner,
mallet, callipers — each one has its own painted shadow, so a missing tool is visible from the
door.

Then someone brings in their own spanner and leaves it on the bench. It is a good spanner. It
works. But now there are two, and the board says nothing about the second one, and when the bolt
rounds off nobody can tell you which spanner did it. The board did not fail. It just stopped being
the only place tools live, and from that moment it stopped being able to tell you anything.

That is what happens the first time you install a package with something other than the tool that
owns the environment. Nothing breaks immediately. The board just stops being true.

## The idea in plain language

Running Python code needs two decisions made: **which interpreter** runs it, and **which packages**
that interpreter can see.

An *interpreter* is the `python` program itself — the thing that reads your file and executes it.
Your machine usually has several. One came with the operating system. One came with a version
manager you installed and forgot. One is inside each project you have ever worked on.

A *package* is code someone else wrote that your code imports. Packages are installed **into a
specific interpreter**, not into your machine generally, which is the fact almost every confusing
Python error traces back to.

A *virtual environment*, or **venv**, is a directory holding one interpreter and its own set of
packages, isolated from every other. One project, one venv, is the rule everybody agrees on.

The part people disagree on is *who creates and updates it*. If the answer is "whoever happens to
be at the keyboard, using whatever tool they remember," then the environment is a shared bench with
no board, and the state of your project is whatever the last command left behind. If the answer is
"one tool, always," then the environment is reproducible: it can be deleted and rebuilt from a file
in the repository, and it will come back identical.

That single tool is the one that owns the environment. This project gives that job to `uv`, and
part [1.2](1.2-uv-and-the-venv-you-never-activate.md) shows what it does with it.

## Why Yantra needs it

Day 76 runs a QLoRA fine-tune where the exact versions of the quantization library and the training
library must agree, and where a mismatch does not raise an import error — it produces a model that
trains and answers badly. Debugging that with an environment nobody owns means you cannot tell a
bad hyperparameter from a bad install.

Nearer than that: on day 176 the CI pipeline builds a container for every service and asserts that
the container and your laptop produce the same evaluation score. That assertion is only meaningful
if your laptop's environment is a file rather than a history.

## The mechanism

There are three commands that install Python packages, and they answer "which interpreter?"
differently. That difference is the whole problem.

```bash
pip install requests        # into whichever interpreter `pip` happens to belong to
python3 -m pip install requests   # into *this* python3, explicitly
uv add requests             # into the project's venv, and record it in pyproject.toml + uv.lock
```

**Line by line:**

- `pip install requests` — the dangerous one. `pip` is itself a program on your `PATH`, and which
  interpreter it installs into depends on which `pip` the shell found first. On a machine with
  three interpreters this is a coin toss you are not aware of making.
- `python3 -m pip install requests` — better, because `-m` means "run the `pip` module *belonging to
  this interpreter*". The ambiguity is gone. But it still installs into whatever `python3` resolves
  to, and it writes nothing down: next week nobody can tell that this package was ever added.
- `uv add requests` — does three things instead of one. It resolves the package against everything
  else already required, installs it into the project's own venv, and **records it** in
  `pyproject.toml` (what you asked for) and `uv.lock` (exactly what you got, down to the hash).
  That last part is why this is the one the project uses: the environment becomes a file, and a
  file can be committed, reviewed and rebuilt.

## When it breaks

Run the first command on a modern Linux and the system stops you:

```text
error: externally-managed-environment

× This environment is externally managed
╰─> To install Python packages system-wide, try apt install
    python3-xyz, where xyz is the package you are trying to
    install.

    If you wish to install a non-Debian-packaged Python package,
    create a virtual environment using python3 -m venv path/to/venv.
    Then use path/to/venv/bin/python and path/to/venv/bin/pip. Make
    sure you have python3-full installed.

note: If you believe this is a mistake, please contact your Python installation or OS distribution
provider. You can override this, at the risk of breaking your Python installation or OS, by passing
--break-system-packages.
hint: See PEP 668 for the detailed specification.
```

*Observed on Ubuntu with Python 3.12.3, 2026-09-07.*

**What it means:** the operating system's interpreter is managed by the operating system's package
manager, and installing into it can break system tools written in Python. The message is not being
awkward; it is telling you that you tried to modify something you do not own.

**The smallest fix:** do not install into the system interpreter at all. Make a venv, and let one
tool own it.

**The trap in the message itself:** it offers you `--break-system-packages`, and that flag works,
which is why people use it. It is named honestly. Reach for it once and the workshop has two
spanners on the bench.

## In production

A professional does not think about this as three commands. They think about it as one rule: **the
environment is a file, not a history.** Everything follows from that.

- **What is written instead of the teaching version.** No engineer types `uv add` in a shared repo
  and moves on. They add it, run the test suite, and commit `pyproject.toml` and `uv.lock` in the
  *same* commit as the code that needs it. A lockfile committed separately from its caller is a
  commit that cannot be checked out and run.
- **What degrades under pressure.** Under a deadline the temptation is to `pip install` the one
  missing thing into whatever is active, "just to see if it fixes it". It usually does fix it,
  locally, which is the problem — the fix does not exist in the repository, so CI still fails, and
  now the local machine and CI disagree for a reason nobody has written down.
- **The failure that only shows with real traffic.** Two services in this project (`yantra-med` and
  `yantra-edge`) will be built into containers from the same lockfile. An unrecorded local install
  means the container is missing a dependency that your laptop has, and you find out at the smoke
  test on day 176 — several layers away from the cause.
- **The review comment.** *"This adds a runtime import but doesn't touch the lockfile — how is this
  meant to install?"* It is the single most common Python review comment there is.
- **The interview question.** *"Your colleague says the tests pass locally and fail in CI. What do
  you check first?"* The answer that shows experience is not "the logs" — it is "whether the two
  environments are built from the same lockfile, and whether that lockfile is committed."

## Check yourself

- **Run:** `which -a python3` — expect **more than one path**. That list is the problem this part
  exists to solve. If it is exactly one, you have a tidier machine than most; the rule still holds.
- **Say out loud:** Why is `pip install X` a worse instruction to give a colleague than
  `uv add X`, even when both of them work?
