## One-line answer

`done N` refusing to commit is the feature, not the friction: it is the only thing standing between
this repository and a set of days that look finished.

## The story

The end-of-shift walk again, but with the sign-off sheet.

The sheet has a line for every machine. You cannot sign the bottom until every line above it is
ticked, and the line you always want to skip is the one for the machine you did not use today —
because you did not use it, so what is there to check?

That is the line that catches the guard someone else left off at lunchtime. The sheet is not
measuring your work. It is refusing to certify a floor it has not been shown.

## The idea in plain language

There are two ways to end a unit of work.

**Declare it done.** You decide it is finished, write the row, and move on. This is what a study
plan does, and it has one structural flaw: nothing in it can go wrong, so nothing in it can be
checked. A day covered thinly and a day covered properly produce the same row.

**Have it refuse.** The tool holds two things you cannot fake — a checklist with unticked boxes,
and a ledger row that does not exist — and declines until both are resolved. Only then does it run
the checks, regenerate the indexes and commit.

The second sounds like bureaucracy. It is the opposite: it is the only way the repository can carry
information about its own quality. A `PROGRESS.md` row that is machine-gated means something. A row
you could have written whenever you liked means nothing, and a reader cannot tell the two apart by
looking.

The refusal is also where the ordering guard lives. `brief N` exits non-zero when day N is not
next, because the plan's ordering *is* the curriculum: a day written early is a day whose
prerequisites were never taught. That is not a warning to acknowledge and route around. Reordering
needs a written decision — an ADR — and the ADR is the point, because it makes you see the cost
before you pay it.

## Why Yantra needs it

Day 219 blocks a pull request when an evaluation score regresses, and posts the delta as a comment.
Day 224 rolls a deployment back automatically when the error rate breaches a threshold.

Both are this same idea with money attached. If you have spent 200 days routing around a gate that
refused you, you will build a pipeline whose gates can be overridden — and a gate that can be
overridden under pressure is not a gate, because pressure is exactly when it matters.

## The mechanism

Watch all three refusals. They are the day's proof that the tooling works, and none of them is an
error in your setup.

```text
$ python granth.py brief 5    ; echo "exit=$?"   # out of order
**STOP.** Day 5 is out of order — day **0** is next.
exit=1

$ python granth.py depth 0    ; echo "exit=$?"   # not written to contract
FAIL  day  0  0 parts
        day 0: no folder in days

1 of 1 day(s) fail the depth contract.
exit=1

$ python granth.py done 0     ; echo "exit=$?"   # not finished
no folder for day 0.
exit=1
```

*Observed 2026-09-07 on this repository, before any day was written.*

**Line by line:**

- `brief 5` → **STOP** — the ordering guard. Note it names which day *is* next rather than only
  saying no, so the refusal is actionable in one read.
- `depth 0` → `FAIL day 0  0 parts` — the parts count is the first thing it reports, because a day
  with no `parts/` is by definition not written, and reporting that before the section-by-section
  detail stops you debugging the contents of a document that does not exist.
- `done 0` → `no folder for day 0.` — the terse one. `done` refuses early and cheaply rather than
  running the full check suite against nothing.
- `echo "exit=$?"` after each — the part that matters for automation. These are not warnings
  printed to a human; they are non-zero exits a script can act on, which is what lets the same
  commands run in CI. **Do not pipe these through `head` or `tail` while testing the exit code** —
  `$?` then reports the exit status of `head`, not of `granth.py`, and you will conclude the guard
  is broken when it is working.

Once the day *is* written, `done` refuses for a different and more interesting reason: an unticked
box in `CHECKLIST.md`, or a missing `docs/PROGRESS.md` row. Those two are the ones you will meet
every day, and neither can be satisfied by the tool on your behalf.

## When it breaks

The refusal that catches people is the one where they are certain the day is finished:

```text
$ python granth.py depth 0
FAIL  day  0  1 parts
        days/day-000-toolchain-skeleton/parts/01-rename-me/1.1-rename-me.md: level 'foundation        # foundation | working | production — a day climbs' is not one of ['foundation', 'working', 'production']
        days/day-000-toolchain-skeleton/parts/01-rename-me/1.1-rename-me.md: frontmatter says day NN but it sits in day 0
```

*Observed 2026-09-07, immediately after `granth.py new 0` scaffolded the day from the templates.*

**What it means:** the scaffold is a template, and the template's frontmatter still has its
explanatory comment attached to the `level` value and `NN` where the day number goes. The checker
read the comment as part of the value, which is why the error text looks absurd — it is quoting
back the entire line.

**The smallest fix:** delete the comments from the frontmatter and set the real values. The
template says so; this is the checker enforcing it.

**Why it is worth seeing:** this is the first failure almost everyone meets, it looks like a broken
tool, and it is a correctly-refused half-finished day. Reading it as a bug is the instinct to
unlearn today, on a day where the stakes are zero.

## In production

- **What a professional writes instead of the teaching version.** They do not add an override flag.
  The moment a gate has a `--force`, the gate's meaning changes from "this is true" to "somebody
  decided this was true", and every downstream reader has to know which. If a gate genuinely needs
  to be bypassed, the bypass is a recorded decision — a written exception with a name on it — not a
  flag in a shell history nobody reads.
- **What degrades under pressure.** Gates are removed on the worst day, not the average one:
  an incident, a deadline, a demo in an hour. That is the argument for making the refusal cheap to
  satisfy rather than easy to skip. A checkbox you can tick in seconds survives a bad Friday; a
  twenty-minute ritual does not.
- **The failure that only shows with real traffic.** A gate nobody has watched fail may be
  asserting nothing. This is not hypothetical — an evaluation harness with a scorer that returns a
  constant will pass every run forever and look like protection. Hence the box in every checklist
  in this curriculum: *break it on purpose, watch it go red, fix it.*
- **The review comment.** *"This adds a `SKIP_CHECKS` env var for local dev. What stops it being
  set in the deployment environment?"*
- **The interview question.** *"Tell me about a check you added that failed on your own work."*
  The answer separates people who have built quality gates from people who have configured them.
  A gate that has only ever failed for other people is a gate you have not tested.

## Check yourself

- **Run:** `python granth.py brief 5; echo "exit=$?"` — expect **STOP**, a statement that day 0 is
  next, and `exit=1`. Run it without a pipe, or the exit code you see will be the pipe's.
- **Say out loud:** What can a `docs/PROGRESS.md` row tell a reader that a row in a hand-written
  study log cannot — and which specific refusal is what makes the difference?
