## One-line answer

`granth.py check` runs lint, format, tests, the depth contract and index freshness over the **whole
repository**, not over today's change — so a day cannot be finished by breaking something that was
working yesterday.

## The story

At the end of a shift the workshop does a walk of the whole floor, not just the bench you were
working at. Every tool back on its shadow, every machine off, the cabinet locked.

It feels redundant. You know what you touched. But the walk is not there to check what you
remember touching — it is there to catch the thing you moved without noticing, three hours ago,
while carrying something heavy. Checking only your own bench finds only the mistakes you already
know about.

## The idea in plain language

A **check** here means a command that either passes or fails, with an exit code a script can read.
Exit code `0` is pass. Anything else is fail. That is the whole contract, and it is why these
commands can be chained by a machine.

This project's gate runs five of them:

- **Lint** — code that is syntactically fine but wrong in a known way: an unused import, a variable
  assigned and never read, a comparison that is always true.
- **Format** — code whose layout does not match the project's one style. Checked, not applied, so
  the gate reports a difference instead of silently rewriting your files.
- **Tests** — the assertions about behaviour, excluding the ones marked as needing a GPU or live
  credentials, so the gate runs on a laptop with neither.
- **The depth contract** — the structural rules from the plan's §20 applied to every written day:
  required sections present and in order, a walkthrough after every code block that carries logic,
  a declared level, at least one part marked as the deliberate failure, and no clock anywhere.
- **Index freshness** — whether the generated documents in `docs/` still match the days they index.
  A stale index is a document that lies, and this is the check that catches it.

The word that matters is **whole**. Every one of these runs across the entire repository. On day 0
that is nearly free. On day 150 it is the only thing standing between you and a curriculum where
day 12 quietly stopped passing three weeks ago.

## Why Yantra needs it

Day 219 makes an evaluation score a merge gate: a pull request is blocked if any service's score
regresses. That pipeline is this same idea with more expensive checks in it, and it only works if
you already believe the underlying claim — that a check is worth running over everything, every
time, rather than over the part you think you changed.

Days 215 and 220 add cost and latency guards to the same pipeline. All three are the end-of-shift
walk of the floor.

## The mechanism

The verbs, and what each one is for:

```bash
python granth.py status        # how many days are complete, what is next
python granth.py brief 0       # the assignment, the gate, and whether 0 is allowed yet
python granth.py depth 0       # day 0 against the depth contract
python granth.py index         # regenerate the derived documents in docs/
python granth.py check         # all five checks, whole repository
python granth.py done 0        # refuse, then check, then regenerate, then commit
python granth.py doctor        # this repository's own wiring
```

**Line by line:**

- `status` — reads `docs/PROGRESS.md` and reports the last row. Cheap, and the right first command
  when returning to the project after a break.
- `brief 0` — prints the assignment *and* enforces ordering. It exits non-zero if the day you asked
  for is not next, which is the guard part [3.2](3.2-the-refusal.md) makes you watch fire.
- `depth 0` — one day against the contract. Run this while writing; it is much faster than `check`.
- `index` — regenerates `TRACEABILITY.md`, `CURRICULUM_INDEX.md`, `TRACKER.md`, `WIKI.md` and the
  entity index. Never edit those five by hand: the next `index` overwrites you, silently. Use
  `index --check` to assert freshness without rewriting, which is what CI wants.
- `check` — the walk of the whole floor. Prefer this over running the five commands yourself: it
  fixes their order, so a formatting failure does not hide a depth failure behind it.
- `done 0` — the ceremony at the end of a day, and the subject of [3.2](3.2-the-refusal.md).
- `doctor` — checks the repository's own wiring rather than its content: is the config readable,
  are the plan's markers intact, do the ledgers exist, is any concept ID assigned to two days. Run
  it when a tool misbehaves, before blaming a day.

Its real output right now:

```text
OK yantra: config, plan markers, ledgers and day map all present.
   229 days planned, 400 IDs assigned, each to exactly one day.
```

## When it breaks

The most common `check` failure on a fresh clone is not your code:

```text
$ python granth.py index --check
granth: these generated documents are stale —
        docs/TRACEABILITY.md
        docs/CURRICULUM_INDEX.md
        docs/TRACKER.md
        docs/WIKI.md
        docs/wiki/day-00.md
        docs/wiki/day-01.md
        docs/wiki/ENTITIES.md
        run `python granth.py index`.
$ echo "exit=$?"
exit=1
```

*Caused 2026-09-07 by appending a line to `docs/TRACEABILITY.md` by hand and re-running
`index --check`. Note that it names seven documents, not one — the checker compares what the days
say against every derived file, so one hand-edit puts the whole derived set out of step.*

**What it means:** a day changed and the generated indexes did not. It is not a problem with the
day. It is a problem with the derived documents, which now disagree with their source.

**The smallest fix:** `python granth.py index`.

**The rule that goes with it:** if a generated index ever disagrees with a day, **the day is right
and the index is stale.** Never resolve the disagreement by editing the index — that is how a
generated file starts holding information that exists nowhere else, right up until the next `index`
deletes it.

## In production

- **What a professional writes instead.** The five checks are not in a README for humans to
  remember. They are a single command, and that command is what CI runs, so the local gate and the
  remote gate cannot drift apart. If your CI runs something your laptop cannot, you have two gates
  and only one of them is tested.
- **What degrades at scale.** `check` is fast on day 0 and slow on day 200, because it re-checks
  everything. That is the cost of the design and it is worth paying, but the mitigation matters:
  run `depth N` while writing and `check` before finishing. A gate that is too slow to run is a
  gate people route around, and a routed-around gate is worse than none because it still looks like
  protection.
- **The failure that only shows with real traffic.** A check that has never failed has never been
  tested. It is entirely possible to write a test suite that passes because it asserts nothing —
  which is exactly why the checklist for every day in this curriculum contains a box that says
  *break it on purpose and watch it go red*.
- **The review comment.** *"CI is green but the lint step isn't in the workflow — it only runs
  locally."*
- **The interview question.** *"Why run the full suite rather than only the tests covering your
  change?"* The answer that shows experience is about coupling you did not know existed — and the
  honest follow-up is that on a large codebase you cannot afford full runs on every commit, which
  is where test selection and merge queues come in.
