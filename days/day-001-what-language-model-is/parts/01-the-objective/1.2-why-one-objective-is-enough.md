## One-line answer

Translation, summarisation and question answering are not separate abilities bolted onto a language
model — they are all the same task, because in text the answer is the thing that comes next.

## The story

The phone keyboard again, but pay attention to what it has quietly learned.

Type *"Dear "* at the start of a message and it suggests names. Type *"Dear "* in a message to your
landlord and it suggests different ones. Type *"the meeting is at "* and it offers times, not
names. Nobody built a name mode and a time mode. Nobody wrote a rule that letters open with names.

The keyboard was only ever asked to do one thing: guess the next word. Everything that looks like
knowing about letters, times and who you write to fell out of doing that one thing over enough of
your messages.

## The idea in plain language

The **training objective** is the single thing a model is optimised to do. For the models this
curriculum deals with, it is: *given the tokens so far, put as much probability as possible on the
token that actually came next.* That is the whole objective. There is no second one.

The surprising part is how much fits inside it, and it fits because of a property of text rather
than a property of the model. Almost anything you would want done to text can be written as a
document whose *continuation is the answer*.

| What you want | The document whose continuation is the answer |
| --- | --- |
| Translation | `English: the cat sat down.` / `French:` |
| Summarisation | *…the article…* / `In summary:` |
| Question answering | `Q: what is the capital of France?` / `A:` |
| Classification | `Review: "waste of money." Sentiment:` |
| Writing code | `# a function that reverses a list` / `def ` |

None of those needs a new objective. Each is a prompt whose most likely continuation, in a model
that has read enough text, is the thing you wanted. This is why *prompting* is a technique at all,
and it is the idea day 108 develops into a discipline.

Two consequences follow, and both matter more than they look.

**Capability is not designed, it is discovered.** Nobody decided the model would be able to do
sentiment classification. Someone tried the prompt. That is a different relationship with a system
than engineers usually have, and it is why evaluation (day 59) is not optional bureaucracy — it is
the only way to find out what you actually have.

**The objective does not contain what you want.** It contains *what came next in the training
data*. Those overlap enormously, and where they come apart you get the entire field of alignment:
the model is not failing at its objective when it produces something confident and wrong: it is
succeeding at an objective that was never "be truthful". Day 57 is where that gap gets a name and
day 58 is where it gets a method.

## Why Yantra needs it

Day 52 fine-tunes a model on medical instruction data using exactly this objective and nothing
else — no task-specific head, no new loss. If you think instruction-following is a separate
capability, the training script will look like it is missing something.

Day 57 then asks why supervised fine-tuning is not enough, and the answer is the second consequence
above. That day is unreadable if this part has not landed.

## The source behind it

> **Language Models are Few-Shot Learners** · `arXiv:2005.14165` · 2020
> https://arxiv.org/abs/2005.14165

It claimed that scaling a model trained on this one objective makes it able to perform tasks it was
never trained on, given only a few examples **in the prompt** and no weight updates at all.

Read it after the parts: [`sources/01-language-models-are-few-shot-learners.md`](../../sources/01-language-models-are-few-shot-learners.md).

## The mechanism

The claim, made checkable: write two prompts that differ only in whether examples are present, and
compare the probability the model puts on the right answer.

```python
import os, torch
from transformers import AutoModelForCausalLM, AutoTokenizer

SHOTS = int(os.environ.get("SHOTS", "4"))

tok = AutoTokenizer.from_pretrained("distilgpt2")
model = AutoModelForCausalLM.from_pretrained("distilgpt2")
model.eval()

EXAMPLES = [("dog", "bark"), ("cat", "meow"), ("cow", "moo"), ("duck", "quack")]
shots = "".join(f"{a} => {b}\n" for a, b in EXAMPLES[:SHOTS])

ids = tok(f"{shots}sheep =>", return_tensors="pt").input_ids
with torch.no_grad():
    probs = torch.softmax(model(ids).logits[0, -1], dim=-1)
print(f"SHOTS={SHOTS}  P(' baa') = {probs[tok(' baa').input_ids[0]].item() * 100:.4f}%")
```

**Line by line:**

- `SHOTS` from the environment — the switch. `0` removes the examples entirely; `4` includes them.
  Everything else about the two runs is identical, which is what makes the comparison mean
  something rather than merely show that some code ran.
- `EXAMPLES[:SHOTS]` — slicing rather than an `if`. At `SHOTS=0` the slice is empty and `shots` is
  the empty string, so the prompt collapses to `"sheep =>"` with no special-casing.
- `f"{a} => {b}\n"` — the format is doing real work. The model has to infer from the examples that
  a line is `input => output`, and it can only do that if every example has the same shape. An
  inconsistent separator is the most common reason a few-shot prompt underperforms.
- `tok(' baa').input_ids[0]` — the **first** token of the answer, with its leading space. Two traps
  here: `' baa'` and `'baa'` are different tokens, and a multi-token answer needs its first token,
  because that is the only one this single distribution predicts.
- `probs[token_id]` — reading the probability of a specific token rather than the top of the list.
  This is what makes the result a number you can compare instead of a transcript you have to judge.

Both runs, over four held-out animals:

```text
$ SHOTS=0 uv run python fewshot.py
SHOTS=0
  P(' baa'   | prompt) =  0.1369%
  P(' oink'  | prompt) =  0.1312%
  P(' roar'  | prompt) =  0.0002%
  P(' neigh' | prompt) =  0.0002%
mean = 0.0671%

$ SHOTS=4 uv run python fewshot.py
SHOTS=4
  P(' baa'   | prompt) =  0.4490%
  P(' oink'  | prompt) =  0.1505%
  P(' roar'  | prompt) =  0.0085%
  P(' neigh' | prompt) =  0.0100%
mean = 0.1545%
```

*Observed 2026-09-07 · `distilgpt2` · torch 2.14.0+cpu · transformers 5.16.1.*

The mean rises from 0.0671% to 0.1545% — roughly 2.3× — with no gradient update anywhere. Four
examples in the prompt changed what the model believes about the next token. That is the paper's
claim, running on a laptop.

## When it breaks

The honest reading of those numbers is that they are *tiny*. 0.15% is not a model that knows what
noise a sheep makes; it is a model that has become slightly less wrong.

That is the limit of the claim, and it is a limit of scale rather than of the idea. The paper's
result is about a 175-billion-parameter model. This demonstration runs on 82 million — roughly
2000× smaller. The direction reproduces; the magnitude does not, and no amount of prompt
engineering on this model will make it.

**What breaks if you forget that:** you conclude either that few-shot prompting does not work
(because 0.15% is nothing) or that it works far better than it does (because 2.3× sounds like a
lot). Both readings come from quoting one of the two numbers without the other, which is why the
mean and the individual probabilities are both printed.

**The check that keeps you honest:** the ablation. If `SHOTS=0` and `SHOTS=4` gave the same mean,
the demonstration would have shown that code ran and nothing else.

## In production

- **What a professional writes instead of the teaching version.** They do not reason about
  few-shot by intuition. They keep a small labelled set and measure zero-shot against k-shot on it,
  because in-context examples cost tokens on **every single request** — the cost is permanent
  while a fine-tune's cost is paid once. Day 69 is where that trade gets made with numbers.
- **What degrades at scale.** In-context examples consume context that retrieval also wants. On day
  127 the RAG prompt has to hold retrieved documents *and* format examples, and something has to
  give. Teams discover this when adding a fifth example silently pushes out a retrieved chunk and
  answer quality drops for reasons nobody can locate.
- **The failure that only shows with real traffic.** Few-shot performance is sensitive to example
  *order* and to the specific examples chosen — a real, measured effect, not folklore. A prompt
  validated on four hand-picked examples can behave differently on the distribution of real inputs,
  which is why day 112's robustness test permutes the examples rather than only checking the happy
  path.
- **The review comment.** *"These four examples were picked because they read well. Were they
  measured against the eval set, or against your intuition?"*
- **The interview question.** *"Why can a model do translation when nobody trained it to
  translate?"* The answer is the table above: because a translation is a continuation, and the
  objective was continuation. The follow-up that separates people who have shipped this is *what
  that buys you and what it does not* — capability you did not design, and no guarantee of
  truthfulness anywhere in the objective.

## Check yourself

- **Run:** the mechanism above at `SHOTS=0`, `SHOTS=2` and `SHOTS=4` — expect the mean to rise
  monotonically. If it does not, that is a real result about a small model, not a bug; note it.
- **Say out loud:** Name three tasks that look like separate abilities and explain why all three
  are the same task — then say what the objective does **not** contain.
