## One-line answer

A language model does not produce text — it produces a number for every token in its vocabulary,
saying how likely that token is to come next, and everything else is what you do with those
numbers.

## The story

Type a message on a phone and three words appear above the keyboard. You wrote *"I'll be there in
about"* and it offers **an**, **a**, **five**.

Two things about that strip are worth noticing, and they are the whole of this part.

The first is that it offered three, not one. It did not decide what you meant. It ranked
candidates and showed you the top of the list.

The second is that the list is much longer than three. Every word the keyboard knows is on it,
somewhere, with some weight. **an** is near the top; **aardvark** is near the bottom; both are on
the same list. The strip only has room for three, so you never see the rest — but the ranking over
the whole vocabulary is what the keyboard actually computed, and the three words are a display
decision made afterwards.

## The idea in plain language

A **token** is the unit a model reads and writes. It is usually not a word — it is a fragment,
often a word with its leading space attached, sometimes a piece of a longer word. Day 2 is about
where tokens come from; today, take them as given and notice only that the model's world is made of
them.

The complete set of tokens a model knows is its **vocabulary**, and it is fixed when the model is
built. Nothing outside it can ever be read or written.

A **probability distribution over the vocabulary** is one number per token, where all the numbers
are between 0 and 1 and they sum to exactly 1. It is a statement of belief spread across every
option: *given everything so far, here is how the next token is likely to go.*

That is what a language model computes. Given a sequence of tokens, it returns a distribution over
the vocabulary for what comes next. Not a word. Not a sentence. One number for every token it
knows.

Everything people talk about as if it were a separate capability is a *consumer* of that
distribution:

- **Generating text** is picking one token from the distribution, appending it, and asking again.
- **Answering a question** is generating text whose prompt happened to be a question.
- **Refusing** is a distribution in which polite-decline tokens outrank the ones that would answer.
- **Confidence** is the shape of the distribution — one token at 97% is a different state from the
  top token at 11%, even though both produce exactly one word on screen.

The phrase to retire is *"the model chose"*. The model ranked. Something else chose, and part
[2.3](../02-the-pass/2.3-the-loop.md) is about what that something is.

## Why Yantra needs it

Day 62 quantizes a model to four bits and asks whether quality dropped. "Quality" there is not a
feeling — it is a measured change in the distribution, and if you think the model emits text you
have no place to measure.

Nearer: day 60 builds an LLM-as-judge, and day 219 makes that judge's score a merge gate. A judge
is a model whose distribution over a small set of tokens is being read as a verdict. That only
makes sense once *distribution* is the thing you believe the model produces.

## The mechanism

Ask a real model for the distribution and look at the top of it. This uses `distilgpt2`, an 82M
parameter model small enough to run on a laptop CPU.

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("distilgpt2")
model = AutoModelForCausalLM.from_pretrained("distilgpt2")
model.eval()

ids = tok("The capital of France is", return_tensors="pt").input_ids
with torch.no_grad():
    logits = model(ids).logits

probs = torch.softmax(logits[0, -1], dim=-1)
top = torch.topk(probs, 5)
for p, i in zip(top.values.tolist(), top.indices.tolist()):
    print("%-12s %6.2f%%" % (repr(tok.decode([i])), p * 100))
print("vocabulary size:", probs.shape[0])
print("probs sum      :", float(probs.sum()))
```

**Line by line:**

- `AutoModelForCausalLM` — *causal* means the model may only look leftward: each position sees the
  tokens before it and none after. That restriction is what makes next-token prediction well-posed,
  and day 9 builds the mask that enforces it.
- `model.eval()` — switches off training-time behaviour such as dropout. Without it the same input
  can give slightly different outputs on each call, which will waste an hour when you are trying to
  reproduce a number.
- `.input_ids` — the tokenizer returns several fields; this is the one holding integer token IDs.
  Shape `(1, 5)`: one sequence, five tokens.
- `torch.no_grad()` — we are not training, so do not build the graph needed for backpropagation.
  Prefer this over letting it default: it roughly halves memory on a forward pass, and on day 65
  that difference decides how many requests fit on a GPU.
- `logits[0, -1]` — the model returns a score for every position, not just the last. `[0]` takes
  the only sequence in the batch; `[-1]` takes the final position, which is the one predicting what
  comes *next*. The earlier positions are predictions too, and part
  [1.3](1.3-cross-entropy-and-perplexity.md) uses them.
- `torch.softmax(..., dim=-1)` — turns raw scores into a distribution. Part
  [2.2](../02-the-pass/2.2-softmax-and-temperature.md) is entirely about this line; here it is
  enough that it is the step producing numbers that sum to 1.
- `torch.topk(probs, 5)` — the phone keyboard's strip. Five is a display choice, not a property of
  the model.

Its real output:

```text
' the'        11.77%
' home'        8.23%
' now'         4.99%
' a'           4.93%
' being'       3.56%
vocabulary size: 50257
probs sum      : 1.000005841255188
```

*Observed 2026-09-07 · `distilgpt2` · torch 2.14.0+cpu · transformers 5.16.1.*

Three things in that output are worth more than the code.

**The vocabulary is 50257 tokens.** The five shown are the visible tip of a distribution that has
an entry for all of them.

**The sum is `1.000005841255188`, not `1`.** Floating-point arithmetic in 32 bits does not sum
exactly. This is normal, it is not a bug, and noticing it now saves you from chasing it later.

**The top answer is `' the'`, not `' Paris'`.** The model was asked for the capital of France and
its most likely next token is the definite article. That is not a mistake being made — it is a
faithful report of what an 82M-parameter model believes, and part
[3.1](../03-synthesis/3.1-the-model-has-no-plan.md) is about why.

## When it breaks

The first failure most people meet is asking for more tokens than the model can hold:

```text
  File "…/transformers/models/gpt2/modeling_gpt2.py", line 576, in forward
    position_embeds = self.wpe(position_ids)
                      ^^^^^^^^^^^^^^^^^^^^^^
  File "…/torch/nn/modules/sparse.py", line 189, in forward
    return F.embedding(
           ^^^^^^^^^^^^
IndexError: index out of range in self
```

*Caused 2026-09-07 by feeding 1200 repetitions of `"hello "` — 1200 tokens — to a model whose
`config.n_positions` is 1024.*

**What it means:** `wpe` is the positional embedding table, with exactly 1024 rows because the
model was trained with a 1024-token context. Position 1024 asks for a row that does not exist, and
the lookup fails the way any out-of-range index fails.

**Why it is worth causing:** the message says `index out of range in self` and mentions neither
context length nor tokens. Nothing in it tells you what you did. Meeting it deliberately now means
recognising it instantly when it appears on day 129 with a chunk that grew too large.

**The smallest fix:** truncate to the model's limit — `tok(text, truncation=True,
max_length=model.config.n_positions)`.

## In production

- **What a professional writes instead of the teaching version.** They rarely call `softmax`
  themselves. Serving engines take a sampling configuration and return tokens. But they read the
  distribution constantly at the edges of the system: log-probabilities are how you build a
  confidence signal, how a classifier-style prompt is scored, and how a router decides a query is
  out of distribution. An engineer who thinks the model emits strings has no access to any of that.
- **What degrades at scale.** The logits tensor is `batch × sequence × vocabulary` in float32. For
  a 50k vocabulary that is 200KB **per token position**, so a batch of 32 at 2048 tokens is over
  12GB for the logits alone. This is why serving engines return only the last position by default,
  and why asking for full logits over a long batch is a reliable way to run a GPU out of memory.
- **The failure that only shows with real traffic.** Confidence collapses silently. A model that
  used to put 90% on the right token and now puts 30% still returns exactly one token, and every
  string-level test still passes. Distribution-level metrics are what catch a quantization or a
  fine-tune that made the model less sure without making it visibly wrong — day 62 is where this
  becomes concrete.
- **The review comment.** *"This logs the generated string. Log the top-k log-probabilities too —
  otherwise we can't tell a confident wrong answer from a coin flip."*
- **The interview question.** *"What does a language model actually output?"* The answer that ends
  the question is: a distribution over the vocabulary at every position, of which generation reads
  only the last — and the follow-up worth volunteering is that this is why sampling parameters
  change behaviour without changing the model at all.
