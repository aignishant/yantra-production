## One-line answer

A forward pass turns a string into integers, the integers into vectors, the vectors into one score
per vocabulary token at **every** position — and generation throws away all but the last.

## The story

The phone keyboard does not read your letters. Somewhere between the glass and the suggestion strip
your taps became numbers, and every step after that was arithmetic on numbers.

You never see that boundary and it does not matter to you. It matters enormously to anyone
debugging the keyboard, because the mistakes that are hardest to find are the ones where the
numbers are wrong in a way that still produces plausible words.

## The idea in plain language

Three transformations happen, in order, and each has a shape you can check.

**String to token IDs.** The tokenizer splits the text into tokens and looks each one up in the
vocabulary, producing a list of integers. Nothing intelligent happens here — it is a lookup. The
result has shape `(batch, sequence)`.

**Token IDs to hidden states.** Each ID indexes a row of the embedding matrix, giving a vector.
Those vectors pass through the model's layers and come out the other end as **hidden states** — one
vector per position, of shape `(batch, sequence, hidden_size)`. Everything the model *does* happens
here, and days 6 through 12 take this step apart completely. Today it is a box.

**Hidden states to logits.** A final linear layer maps each position's vector to one score per
vocabulary token, giving shape `(batch, sequence, vocab_size)`.

A **logit** is a raw, unnormalised score. It is not a probability: it can be negative, it can be
large, and the logits at a position do not sum to anything in particular. Turning them into a
distribution is part [2.2](2.2-softmax-and-temperature.md)'s job.

The detail that surprises people is the middle dimension. The model computes a full set of logits
at **every** position, not just the last. Position 0's logits are its prediction of token 1;
position 3's are its prediction of token 4. Feeding a five-token prompt produces five predictions,
of which generation uses exactly one — the last.

That is not waste. It is why training is efficient: one forward pass over a sequence of length *n*
yields *n* supervised predictions at once, which is what part
[1.3](../01-the-objective/1.3-cross-entropy-and-perplexity.md) averaged over. And it is why the KV
cache exists on day 20 — at generation time those earlier positions are recomputed identically on
every step unless something stops them.

## Why Yantra needs it

Day 19 measures how much work the naive version repeats, and day 20 fixes it with a cache. Neither
day makes sense unless you can already see that a forward pass computes *n* positions and
generation reads one.

Day 21 then does the memory arithmetic for that cache — batch × sequence × layers × precision — and
that arithmetic is all shapes. If shapes are vague now, the number that decides how many requests
fit on a GPU will be vague too.

## The mechanism

Follow one prompt through all three stages, printing the shape at each.

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("distilgpt2")
model = AutoModelForCausalLM.from_pretrained("distilgpt2"); model.eval()

text = "The capital of France is"
ids = tok(text, return_tensors="pt").input_ids
print("text  :", repr(text))
print("ids   :", ids.tolist()[0])
print("tokens:", [tok.decode([i]) for i in ids[0].tolist()])

with torch.no_grad():
    logits = model(ids).logits

print("logits shape:", tuple(logits.shape))
last = logits[0, -1]
print("last-position logits: min %.2f max %.2f" % (last.min(), last.max()))
```

**Line by line:**

- `[tok.decode([i]) for i in ids[0].tolist()]` — decoding each ID **separately** to see the token
  boundaries. Decoding the whole list at once gives back the original string and hides exactly what
  you are trying to look at. This one-liner is the most useful debugging tool of the next thirty
  days.
- `model(ids).logits` — the forward pass. No `labels` this time, so no loss is computed; the model
  returns scores only.
- `tuple(logits.shape)` — printed on purpose. Shape assertions catch more real bugs in this
  curriculum than any other check, because a wrong shape usually still runs.
- `logits[0, -1]` — batch 0, last position. Everything about generation lives at this index.
- `last.min()`, `last.max()` — printed to make the point that these are not probabilities. Expect
  both to be negative and neither to be near 0 or 1.

Its real output:

```text
text  : 'The capital of France is'
ids   : [464, 3139, 286, 4881, 318]
tokens: ['The', ' capital', ' of', ' France', ' is']
logits shape: (1, 5, 50257)
last-position logits: min -85.54 max -57.38
```

*Observed 2026-09-07 · `distilgpt2` · torch 2.14.0+cpu · transformers 5.16.1.*

Read the shape `(1, 5, 50257)` as: one sequence, five positions, one score per vocabulary token.
That is 251,285 numbers produced to generate one token.

And look at the tokens. Four of the five carry a **leading space**: `' capital'`, not `'capital'`.
The space belongs to the token. This is the single most common source of confusion when scoring a
specific answer, and it is why part
[1.2](../01-the-objective/1.2-why-one-objective-is-enough.md) scored `' baa'` rather than `'baa'`.

The logits run from −85.54 to −57.38. All negative, none near 1, spanning about 28. Only the
*differences* between them carry meaning — adding a constant to every logit changes nothing after
the next step, which is exactly what part [2.2](2.2-softmax-and-temperature.md) explains.

## When it breaks

Ask a tokenizer to batch two strings of different lengths without telling it how:

```text
ValueError: Unable to create tensor, you should probably activate truncation and/or padding with
'padding=True' 'truncation=True' to have batched tensors with the same length. Perhaps your
features (`input_ids` in this case) have excessive nesting (inputs type `list` where type `int` is
expected).
```

*Caused 2026-09-07 by `tok(["The capital of France is", "Hi"], return_tensors="pt")`.*

**What it means:** a tensor is rectangular. Two sequences of different lengths cannot share one
without a rule for making them equal, and the tokenizer will not guess.

**The smallest fix:** `tok([...], return_tensors="pt", padding=True)` — and for GPT-2 specifically,
`tok.pad_token = tok.eos_token` first, because it was trained without a padding token at all.

**The trap behind the fix:** padding introduces positions that mean nothing, and if you then read
`logits[:, -1]` you may be reading the logits *of a pad token*. For left-padded batches that is
correct; for right-padded ones it is silently wrong, and the output is plausible text from the
wrong position. Day 65 meets this properly when batching real requests.

## In production

- **What a professional writes instead of the teaching version.** They almost never call the model
  directly. A serving engine handles tokenizing, batching, padding and returning only the last
  position. But they read shapes constantly at the boundaries, and the first thing anyone does with
  a model that behaves oddly is print the token list — because roughly half of "the model is
  broken" turns out to be "the text was tokenized differently than assumed".
- **What degrades at scale.** The logits tensor is `batch × sequence × vocab`. At float32 and a 50k
  vocabulary that is about 200KB per position, so a batch of 16 at 1024 tokens is over 3GB for
  logits alone — for a model whose weights are smaller than that. Serving engines return only the
  last position by default for this reason, and asking for full logits on a long batch is a
  reliable out-of-memory error.
- **The failure that only shows with real traffic.** Padding-side bugs. A single request works
  perfectly; a batched request returns fluent output derived from a pad position. Every string test
  passes because the output is well-formed text. It shows up as a mysterious quality drop that
  correlates with load, which is the hardest kind of bug to attribute.
- **The review comment.** *"This reads `logits[:, -1]` on a right-padded batch — for the shorter
  sequences that's a pad position, not the last real token."*
- **The interview question.** *"You feed a five-token prompt. What shape comes back and why isn't
  it just one row?"* The answer that opens the door to the next twenty days is that the model
  predicts at every position, generation uses one, and the gap between those two facts is where the
  KV cache lives.

## Check yourself

- **Run:** the mechanism above, then change the prompt to `"The capital of France is "` — with a
  trailing space — and compare the token lists. Expect them to differ, and expect the prediction to
  get **worse**, because the space is now its own token instead of part of the next one.
- **Say out loud:** Why does a five-token prompt produce five sets of logits when generation only
  needs one — and name the day that turns that observation into a performance fix.
