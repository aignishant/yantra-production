## One-line answer

Generation is a loop outside the model: predict one token, append it to the input, feed the whole
thing back, repeat — which means the model is called once per token and has never seen a sentence
it has not already written.

## The story

Tap the middle suggestion on your phone. A word appears. Now the strip refreshes with three new
suggestions, based on the sentence including the word you just tapped.

Keep tapping the middle one. Ten taps in you have a sentence, and it is usually strange — it drifts,
it repeats, it commits early to a phrasing and then has to live with it. You did not write that
sentence and neither did the keyboard. It was assembled, one tap at a time, by a thing that only
ever answered *what next* and never once answered *what am I trying to say*.

That loop is the whole of text generation. Everything that feels like a model composing a paragraph
is you tapping the middle suggestion very fast.

## The idea in plain language

The model maps a sequence to a distribution over the next token, and that is all it does. It has no
memory between calls, no notion of a sentence in progress, no plan.

**Autoregressive generation** is the loop wrapped around it:

1. Run the model on the current sequence.
2. Take the logits at the last position.
3. Choose one token from them.
4. Append that token to the sequence.
5. Go to 1, until you hit a stop token or a length limit.

Three consequences follow, and they explain most of what is strange about working with these
models.

**The loop is not in the model.** It is in your code, or in a serving engine's code. This is why
`generate()` has so many parameters: every one of them is a decision made in step 3 or step 5, not
a property of the weights.

**Step 3 is a policy, not a fact.** *Greedy* takes the highest-probability token every time.
*Sampling* draws from the distribution, optionally shaped by temperature (part
[2.2](2.2-softmax-and-temperature.md)), top-k or top-p. Same model, same beliefs, completely
different output.

**Each token costs a full forward pass over the whole sequence.** Generating 100 tokens means 100
calls, each one longer than the last. A naive implementation redoes all the work for every previous
position on every single step, which is precisely the waste day 19 measures and day 20 removes.

## Why Yantra needs it

Day 19 measures the cost of this loop and day 20 introduces the KV cache to fix it. Day 68 attacks
the same cost differently with speculative decoding — a small model drafting several tokens for a
large one to check in a single pass. Neither idea is available to you if generation is a black box
called `generate()`.

Day 174 builds a ReACT agent, which is this same loop with tool calls interleaved: predict, act,
observe, append, repeat. Agents are not a different mechanism. They are this loop with a wider
step 4.

## The mechanism

Write the loop by hand. Twelve steps, greedy, no library helper.

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("distilgpt2")
model = AutoModelForCausalLM.from_pretrained("distilgpt2")
model.eval()

cur = tok("The capital of France is", return_tensors="pt").input_ids
for _ in range(12):
    with torch.no_grad():
        nxt = model(cur).logits[0, -1].argmax()
    cur = torch.cat([cur, nxt.view(1, 1)], dim=1)

print(repr(tok.decode(cur[0])))
```

**Line by line:**

- `for _ in range(12)` — the loop is here, in plain Python, outside the model. Nothing inside the
  model knows this is happening.
- `model(cur)` — the **whole** sequence, every time. On the first pass that is 5 tokens; on the
  last it is 16. Every earlier position is recomputed from scratch on every iteration, and the
  results are identical each time. Seeing that waste written plainly is the point of hand-rolling
  this before day 20 shows you the cache.
- `.logits[0, -1]` — the last position only, exactly as part
  [2.1](2.1-from-string-to-logits.md) described. The other positions are computed and discarded.
- `.argmax()` — step 3, greedy. This is also the honest implementation of `temperature=0`, avoiding
  the division part [2.2](2.2-softmax-and-temperature.md) showed produces `nan`. Note there is no
  softmax anywhere: the highest logit is the highest probability, so normalising would change
  nothing and cost time.
- `nxt.view(1, 1)` — reshaping the scalar to `(batch, sequence)` so it can be concatenated.
  `torch.cat` requires matching dimensions everywhere except the one being joined; forgetting this
  is a shape error, which is the good outcome.
- `dim=1` — joining along the sequence axis. `dim=0` would stack it as a second sequence in the
  batch and run silently, generating nothing and telling you nothing.
- **No stop condition.** Real generation halts on an end-of-sequence token. This loop runs exactly
  twelve times regardless, which is why the output ends mid-sentence.

Its real output:

```text
'The capital of France is the capital of the French Republic. The capital of France is'
```

*Observed 2026-09-07 · `distilgpt2` · torch 2.14.0+cpu · transformers 5.16.1.*

Read it carefully, because it is more informative than a good answer would have been.

It is **grammatical**. It is **circular** — "the capital of France is the capital of…" defines the
thing by itself. And by token twelve it has looped back to repeating its own opening verbatim.

Nothing malfunctioned. Every step took the single most probable token given everything so far, and
this is where that lands. Part [3.1](../03-synthesis/3.1-the-model-has-no-plan.md) is about why.

## When it breaks

The loop's characteristic failure is that it does not stop:

```text
'The capital of France is the capital of the French Republic. The capital of France is the capital
of the French Republic. The capital of France is the capital of the French Republic. The capital of
France is the capital of the French
Republic.\n\n\n\n\n\n\n\n\n\n\n\n\n\n\n\n\n'
```

*Observed 2026-09-07 by raising the loop bound from 12 to 60 with everything else unchanged.*

**What it means:** greedy decoding is deterministic, so once the model reaches a state it has
already been in, it produces the same continuation, which returns it to the same state. It is a
cycle, and nothing in the loop can detect one.

Then look at the tail. After four cycles it stops repeating and emits seventeen consecutive
newlines. That is the second failure mode of a loop with no stop condition: having exhausted the
phrasing, the most probable token becomes whitespace, and whitespace predicts more whitespace. In a
production system those seventeen newlines are seventeen billed tokens carrying nothing.

**The three real fixes, in the order they are reached for:** a repetition penalty that lowers the
logits of recently emitted tokens; sampling instead of greedy, so the cycle is broken by chance;
and a stop condition that is not merely a token budget. Production systems use all three.

**Why greedy is still the right default for testing:** it is reproducible. Day 210's prompt
regression tests depend on identical input giving identical output, and that is only true here.

## In production

- **What a professional writes instead of the teaching version.** Nobody ships this loop. A serving
  engine runs it with a KV cache, continuous batching, and stop conditions — but every parameter in
  its API is a knob on one of these five steps, and engineers who have written the loop once read
  that API as a description of a mechanism rather than a list of magic words.
- **What degrades at scale.** The two phases of generation have completely different performance
  characteristics. *Prefill* processes the whole prompt in one pass and saturates the GPU's compute.
  *Decode* produces one token per pass and is limited by memory bandwidth, because it reads the
  entire model's weights to produce a single token. This is why the first token is slow and the
  rest are fast, why time-to-first-token and tokens-per-second are reported separately, and why
  day 95's benchmark measures both.
- **The failure that only shows with real traffic.** Cost is linear in output tokens and nearly
  free in input tokens by comparison, because input is one prefill pass and output is one full pass
  per token. A prompt change that makes responses longer without making them better is a permanent
  bill increase that no quality metric will flag. Day 216's cost regression guard exists for
  exactly this.
- **The review comment.** *"`max_new_tokens` is 4096 with no stop sequence. What happens when the
  model doesn't stop on its own?"*
- **The interview question.** *"Where is the generation loop?"* If the answer is "inside the
  model", the follow-up about the KV cache has nowhere to go. The loop is outside; the model is a
  pure function from sequence to distribution; everything interesting about serving lives in the
  gap.
